## 2. 背景与当前状态

现有耳机研究看板把两类职责放在同一个应用中：

1. **项目制作**：读取 CSV、识别变量角色、扫描照片、配置映射规则、人工校正、生成项目 JSON、复制 CSV 与照片。
2. **项目分析**：透视分析、挤压机制、设备偏好、照片对比和多项目分析。

当前首页“数据预处理”已经包含较完整的业务能力，但与分析页、浏览器文件权限、本地 HTTP 服务和多套照片 URL 路由耦合。照片检查依赖 HTML 图片元素逐步请求、解码和缩略；随着照片数量与原图尺寸增加，需要叠加懒加载、缩略图接口、缓存和多来源路由，性能与故障定位都变复杂。

上一版 project-builder 原型只完成了 CLI、字段自动识别、基础映射、审计列表和项目文件夹写出。它不作为目标产品继续扩建，缺口包括：

- 未完整迁移现有首页的变量分类和映射配置能力。
- 无法逐用户、逐设备、逐耳侧、逐视角查看真实照片映射。
- 无法完成拖拽交换、单张替换、整组移动、左右耳互换和空耳槽位编辑。
- 新建项目与更新已有项目没有被区分。
- 无法明确控制“只更新 CSV”“只更新照片”“同时更新”及对应保留规则。
- 产品仍是浏览器页面，照片展示仍受 HTML 图片加载链路制约，没有形成独立强后端。

## 3. 产品边界与责任划分

### 3.1 项目制作器负责

- 新建、打开、检查、更新和发布项目包。
- 读取并保留原始 CSV。
- CSV 编码、表头、行数据和项目模板校验。
- 自动识别及人工确认变量角色。
- 扫描、索引、复制和更新照片资产。
- 自动照片映射和完整的人工映射校对。
- 显示发布前差异，按用户选择的更新范围执行事务。
- 生成看板兼容项目 JSON、审计报告和可重建的本地索引。
- 提供 Windows 原生桌面程序和 Linux 无界面 CLI。

### 3.2 看板负责

- 继续读取原始 CSV、项目 JSON 和照片目录。
- 继续执行现有自动照片映射并展示映射结果。
- 继续支持单张替换、拖拽交换、设备组移动、左右耳互换及空耳照片调整。
- 继续支持变量类别自动识别、拖动/下拉更换、确认和恢复，尤其不得把变量类别固化为只读。
- 继续支持从首页新建、编辑和保存项目包，作为研究人员熟悉的完整工作入口。
- 打开已发布的项目包。
- 单项目和多项目数据分析。
- 分析布局、筛选、排序、用户备注等分析状态。

“项目制作与看板分析分离”指新增一条不依赖看板即可完成项目包生产和自动化的路径，不代表从看板删除、隐藏或降级原有数据准备能力。MVP 期间两条路径并存，生成相同兼容格式的项目包。

### 3.3 不在本期范围

- 修改统计分析、挤压机制、设备偏好和照片对比算法。
- AI 图像内容识别或自动判断拍摄角度。
- 云端项目协作、审批和多人并发编辑。
- 在线账户、用户权限和远程照片托管。
- 原图编辑、裁剪、标注和画质增强。

## 4. 问题陈述

### 4.1 用户问题

**I am…** 需要定期整理耳机研究 CSV 和大量佩戴照片的研究人员。  
**I am trying to…** 在分析前得到一个结构正确、映射可核对、可以跨机器使用的项目包。  
**But…** 当前必须在分析看板中完成数据准备，而且无法独立、明确地控制本次只更新 CSV 还是同时更新照片。  
**Because…** 项目制作、浏览器文件访问、图片加载和看板分析共享同一套状态与界面，更新事务也没有被显式建模。  
**Which makes me feel…** 不敢确认映射是否正确，也担心一次更新误覆盖已有照片、映射或分析配置。

### 4.2 技术与业务问题

**I am…** 维护耳机研究数据工具的产品与工程团队。  
**I am trying to…** 让项目生产过程可自动化、可验证、可回滚，并同时服务 Windows 人工操作和 Linux 批处理。  
**But…** 现有映射依赖前端状态，照片需要经过多层 HTTP/HTML 加载优化，项目更新缺少稳定身份键和事务边界。  
**Because…** 数据准备最初作为看板的一页逐步生长，没有独立的领域模型、索引、差异引擎和发布流程。  
**Which makes me feel…** 每增加一种照片来源或更新方式都会扩大耦合，并提高数据损坏和兼容回归风险。

## 5. 理想状态

**In a perfect world:** 用户既可以继续在看板中完成熟悉的数据准备，也可以打开一个独立原生项目制作器，选择新建或更新项目，读取 CSV 和/或照片后看到完整的数据结构与真实照片映射；程序明确展示本次将修改和保留的内容，经确认后原子发布项目包。Linux 使用相同的项目制作器后端核心无界面批量执行。

**The biggest benefit to me is:** 项目生产和数据分析真正分离，映射结果可见、更新范围可控、照片处理由高性能后端承担。  
**Which makes me feel:** 我能在打开看板前确认项目是正确的，并敢于自动化重复的数据准备工作。

## 6. 产品原则

1. **先预览，后发布**：任何写入前必须展示结果与差异。
2. **更新范围显式选择**：不得仅因用户选择过某个目录就隐式更新该资产。
3. **照片映射必须可见**：统计数字不能替代逐槽位照片核对。
4. **保留优先**：未被选中的资产、人工映射和分析配置必须原样保留。
5. **稳定身份而非行号**：更新时用业务身份键关联记录，不以 CSV 行号关联人工映射。
6. **原子发布、可回滚**：失败不得留下半个项目包。
7. **同核双入口**：Windows GUI 与 Linux CLI 使用同一个后端领域核心和测试夹具。
8. **项目兼容优先**：当前看板无需重新映射即可读取生成结果。
9. **双入口等权**：独立制作器是新增生产入口，不以削减看板现有功能作为交付条件。

## 8. 目标用户

### Persona A：Windows 研究人员

- 使用 GUI 新建和更新项目。
- 需要可视化检查照片是否属于正确用户、设备、耳侧和视角。
- 需要在异常用户内拖动或重新选择照片。

### Persona B：Linux 自动化维护者

- 通过 CLI、cron 或 systemd 批量生成项目。
- 需要稳定配置、明确退出码、结构化日志和审计报告。
- 遇到不确定映射时需要任务失败，而不是静默猜测。

### Persona C：看板分析用户

- 可以只打开已经发布的项目，也可以继续直接读取 CSV 和照片创建或修改项目。
- 需要继续更换变量类别、查看和调整照片映射。
- 希望照片与数据加载稳定，分析配置不被项目更新意外重置。

~~~text
项目中心

├── 打开已有项目
└── 最近项目

项目工作区
├── 01 CSV 数据：原表预览 / 数据质量 / 变量分类
├── 02 照片来源与规则：索引 / 映射方式 / 耳侧设备视角空耳
├── 03 映射检查：照片矩阵 / 人工调整 / 异常与未使用照片
└── 04 发布项目：更新范围 / 差异预览 / 校验 / 发布与回滚
~~~

主状态流：

~~~text
选择输入 → 后端读取/索引 → 生成工作草稿 → 人工校对
       → 选择更新范围 → 计算项目差异 → 校验 → 原子发布 → 看板兼容读取/继续编辑
~~~

草稿状态与已发布项目状态必须分离。前三页只修改工作草稿；只有“发布项目”可以修改项目包。

## 10. 更新模式与事务语义

发布页必须明确选择模式，不提供含糊的通用“保存项目”按钮。

| MODE | CSV / DATA | PHOTO ASSETS | PHOTO MAPPING | DASHBOARD CONFIG / NOTES |
|---|---|---|---|---|
| **新建项目** | 写入 | 可选写入 | 生成 | 使用模板默认值 |
| **仅更新 CSV** | 替换 | 原样保留，不扫描、不复制、不删除 | 按稳定行键保留；新增记录可用项目现有照片补映射 | 原样保留 |
| **仅更新照片** | 原始 CSV 与 mappingRows 原样保留 | 按选择策略更新 | 使用现有 CSV 重算；有效人工映射优先保留 | 原样保留 |
| **更新 CSV + 照片** | 替换 | 按选择策略更新 | 基于新数据和新资产重算，再叠加有效人工映射 | 原样保留 |
| **仅更新映射** | 原样保留 | 原样保留 | 保存人工调整与映射规则 | 原样保留 |

### 10.1 仅更新 CSV

- 不读取外部照片根目录。
- 不修改项目 photos 目录下任何文件、时间戳或目录。
- 不重置 photoRoot、mappingMode、mappingViews 和有效人工映射。
- 用稳定行键把原 rows 中照片字段迁移到新记录。
- 新增记录如果能从项目现有照片唯一匹配，可以自动补齐；否则留空并进入异常清单。
- 被删除记录对应的照片不自动删除，只标记为“当前 CSV 未使用资产”。

### 10.2 照片更新策略

- **合并（默认）**：新增文件；同相对路径且内容变化的文件列为待替换；不删除项目独有照片。
- **镜像**：项目照片与新来源完全一致；所有删除项在差异页单独列出并二次确认。
- **只索引不复制（P1）**：面向固定 Linux 存储，仅保存受控相对引用；项目不保证可独立搬运。

文件相等先使用相对路径、大小和 mtime；发生冲突或严格校验时计算内容哈希。

### 10.3 稳定行键

- 默认由“用户编号 + 设备/条件 + 耳侧 + 用户确认的附加条件字段”组成。
- 发布前必须保证行键唯一；不唯一时阻断发布。
- 后端人工映射使用 stableRowKey + photoField 保存。
- 写出当前兼容 JSON 时，再转换为看板现有行数据和必要兼容字段，不继续依赖 rowIndex::field。

### 10.4 原子发布与回滚

1. 在项目同盘临时目录构建完整候选版本。
2. 校验 JSON、CSV、照片引用、资产数量和稳定行键。
3. 生成发布计划和审计报告。
4. 用户确认后，保留最近一个可恢复版本并原子切换。
5. 任一步骤失败，原项目保持不变。

## 11. 关键功能

### 11.1 项目中心

- 新建项目、打开项目 JSON/文件夹、最近项目。
- 显示标题、路径、最近发布时间、CSV 行数、照片数量和异常状态。
- 修改项目名时同步处理文件夹和主 JSON 文件名，并预览路径变化。
- 损坏或不完整项目进入只读恢复检查，不直接覆盖。

### 11.2 CSV 读取与原表检查

- 支持拖放、文件选择和 CLI 路径。
- 支持 UTF-8、UTF-8 BOM、GB18030；无法可靠判断时要求用户选择编码。
- 展示原始表头、总行数、前 N 行、空值率、唯一值数和数值识别。
- 检查空/重复表头、列数错位、用户编号缺失、身份键重复、数值范围和组内一致性。
- 原始 CSV 按用户选择的更新模式保存，不被格式化重写。

### 11.3 变量分类

完整支持当前角色：用户编号、设备/条件、组间变量、人耳尺寸、记录分组变量、干涉变量、评分/数值指标、挤压程度、照片、忽略。

- 自动识别、拖动分类、下拉分类和恢复自动识别。
- 显示自动结果与人工结果差异。
- 保持唯一用户编号、系统照片字段等锁定规则。
- 人工改动显式确认后才进入草稿。
- 支持项目模板的必填字段、建议字段、数值范围、字段角色和照片 schema。

### 11.4 照片索引与强后端

- 后端直接遍历文件系统，不通过浏览器上传文件列表。
- 使用 SQLite 保存相对路径、大小、mtime、哈希状态、EXIF 方向和缩略图状态。
- 首次扫描增量生成缩略图；再次打开只处理新增和变化文件。
- 缩略图由后端进程池生成，完成 EXIF 旋转和尺寸限制。
- UI 只接收当前可见范围的原生缩略图对象，不加载原始大图。
- 原图只在打开单张大图时按需解码，并限制并发与内存缓存。
- 索引和缩略图可删除重建，不作为项目事实来源。

### 11.5 照片规则

- **照片顺序逻辑**：按用户目录与文件名自然排序，按设备记录顺序 × 视角顺序映射。
- **子文件夹逻辑**：姓名/用户、耳侧、设备、方向层级顺序不限。
- 用户字段必选；耳侧和设备字段可不配置。
- CSV 无耳侧但照片区分左右耳。
- 自动/强制单耳模式。
- 顺序模式下空耳照片、左右耳分别计数、空耳标签自定义。
- 项目模板提供预期耳侧和视角。
- 未配置设备但存在多套设备目录时，必须提示所选设备，不静默处理。

### 11.6 可视化映射检查

这是 P0 核心能力，不能用纯文本审计替代。

- 按用户展示预期/实际照片数及正常、缺失、过多状态。
- 每个用户内按设备 → 耳侧 → 视角展示真实缩略图槽位。
- 槽位显示视角、相对路径、文件名及人工/自动来源。
- 点击查看原图和完整文件信息。
- 同用户内拖动交换两个槽位。
- 单槽位从候选照片中重新选择或设为空。
- 顺序模式支持设备整组上移/下移。
- 左右耳照片组一键互换。
- 空耳照片可与设备照片重新分配，显示名称可编辑。
- 支持撤销/重做、恢复某用户自动映射、恢复全部自动映射。
- 支持正常/缺失/过多/重复/人工调整筛选，以及用户和设备搜索。
- 独立展示未使用照片和重复/补拍照片，并可分配到空槽位。
- 调整后实时更新异常数量，但不直接写入项目包。

### 11.7 发布前差异

发布页分别列出：

- CSV：新增、删除、修改记录和字段变化。
- 照片：新增、替换、保留、删除和未使用文件。
- 映射：新增、改变、失效和人工保留槽位。
- 项目 JSON：将改变的顶层字段。
- 明确保留的分析配置、用户备注和用户排序。

镜像删除、失效人工映射和身份键变化属于高风险变更，必须单独确认。

### 11.8 审计与自动化

- GUI 可导出缺失/异常 CSV、发布计划 JSON 和构建摘要。
- 每次发布保存机器可读审计：输入摘要、更新模式、规则、差异、警告、结果和版本。
- Linux CLI 支持配置文件、环境变量覆盖、JSON 输出和结构化日志。
- 退出码：0 成功；1 输入/系统错误；2 数据或映射失败；3 发布冲突；4 用户取消或策略阻断。
- strict 模式下，缺失、重复、不唯一身份键或未确认推断均阻断发布。
- dry-run 生成与 GUI 一致的差异和审计，但不写项目。

## 13. 第一版 MVP 定义（待 Hanson 审阅）

### 13.1 MVP 目标

交付一个能够在 Windows 上独立完成真实项目制作、在 Linux 上无界面执行相同构建核心、并且不改变看板现有能力的首版。MVP 必须能被日常项目使用，不能以“只能生成基础 JSON、无法查看或调整真实照片”为完成标准。

### 13.2 MVP 必须包含

| AREA | MVP SCOPE | RELEASE GATE |
|---|---|---|
| 看板保留 | 看板现有 CSV/JSON/照片读取、变量类别更换、自动映射、人工照片调整和项目保存功能全部保留 | 现有前后端测试通过；人工回归关键首页流程 |
| Windows 原生程序 | PySide6 GUI，可新建和打开已有项目；发布兼容项目包 | 在本地 Windows 10/11 构建并启动 EXE；不通过云端 CI 代构建正式 EXE |
| CSV 读取 | UTF-8、UTF-8 BOM、GB18030；表头/行预览；原始数据与基础异常检查 | 使用现有真实 CSV 成功读取且不改变原文件 |
| 变量分类 | 完整显示现有变量角色；自动识别；拖动或下拉更换；确认；恢复自动结果；项目模板约束 | 同一夹具与看板分类结果一致；人工更换写入项目 JSON 后看板正确识别 |
| 照片后端 | 直接扫描目录；SQLite 增量索引；后端缩略图；EXIF 方向处理；缓存重用 | 第二次打开不全量重建；坏图不导致程序崩溃 |
| 自动映射 | 覆盖顺序和子文件夹模式，以及用户、设备、耳侧、视角、单耳和空耳规则 | 共享黄金夹具结果与看板现有逻辑一致 |
| 映射可视化 | 按用户→设备→耳侧→视角显示真实缩略图、文件名、来源及缺失/过多状态；支持查看原图 | 任一映射槽位都能追溯到实际文件 |
| 人工调整 | 单槽位选择/清空、拖拽交换、设备组移动、左右耳互换、空耳重新分配、恢复自动映射 | 保存、关闭、重新打开后人工调整不丢失 |
| 更新控制 | 新建、仅 CSV、仅照片、CSV+照片、仅映射五种模式；MVP 照片资产只采用安全的“合并”策略 | 未选中的资产和配置在自动化校验中保持不变 |
| 发布安全 | 写入前摘要与差异；同盘暂存；候选包校验；原子替换；失败保留原项目 | 模拟中断时原项目仍可由看板打开 |
| Linux CLI | 同一 Python 核心支持配置文件、dry-run、strict、结构化结果及五种模式；首版以 Python 可执行入口交付 | 在 Linux x64 无图形环境运行；与 GUI 输入的 JSON 语义一致 |
| 兼容输出 | 保持项目 JSON version 1 和现有字段语义；复制所选 CSV/照片；输出映射异常 CSV | 当前看板无需迁移即可继续读取、调整和保存 |

### 13.3 MVP 明确暂缓

- 照片“镜像”策略及自动删除项目照片；MVP 只合并，不自动删除。
- 引用外部或网络共享照片而不复制进项目包。
- 多版本历史管理和可视化版本恢复；MVP 只保留一次安全备份/失败回滚。
- 跨项目规则预设、批量项目队列和计划任务管理界面。
- Linux 桌面 GUI、Linux 单文件可执行程序及 Linux ARM64。
- AI 图像识别、拍摄方向判断、重复照片视觉识别。
- 全量 10,000+ 照片性能优化作为发布阻断项；MVP 先以典型真实项目规模验收，并记录基线。

### 13.4 MVP 端到端验收场景

1. 在 Windows 原生程序中读取一份真实 CSV，更换至少两个字段的变量类别并确认。
2. 选择真实照片目录，分别验证顺序模式和子文件夹模式中的至少一种，并看到全部映射缩略图。
3. 完成一次单张替换、一次照片交换、一次左右耳或设备组调整，保存并重新打开验证结果。
4. 新建项目包后，用现有看板打开；在看板中再次更换变量类别和调整照片映射并保存。
5. 分别执行仅 CSV、仅照片、CSV+照片、仅映射更新，校验未选中内容保持不变。
6. 使用同一配置在 Linux CLI dry-run 和正式构建，比较 Windows GUI 结果的 JSON 语义与照片资产清单。
7. 人为制造重复稳定键、缺失照片、坏图和写入中断，确认提示明确且不破坏原项目。

### 13.5 MVP 完成定义

以下条件全部满足才进入用户审阅版：

- MVP 表格中所有 release gate 均有测试或人工验收证据。
- 现有看板功能没有删除、隐藏、默认禁用或字段兼容回归。
- Windows EXE 必须在本地 Windows 环境构建并完成启动测试；仓库提供可复现构建脚本和说明。
- Linux CLI 至少在一个 Linux x64 环境完成无界面端到端构建测试。
- 用同一真实项目比较“看板生成”和“制作器生成”，看板均能打开并继续编辑。
- 已知差异、性能基线和未完成项写入发布说明，不以静默降级通过验收。

## 14. 非功能需求

### 14.1 技术架构（提议）

- **桌面 UI：Python 3.11+ / PySide6（Qt）原生控件。** 不使用浏览器、Electron或本地网页作为正式 GUI。
- **领域核心：Python 独立包。** CSV、索引、映射、差异、事务和审计均在后端实现。
- **Linux：同一 Python 核心提供 headless CLI。** 不要求 X Server，可由 cron/systemd 调用。
- **本地索引：SQLite。**
- **图片处理：Pillow 后端进程池 + Qt 原生图像展示。**
- **Windows 分发：PyInstaller onedir。** 只允许在本地 Windows 机器构建和验证；CI 不编译或提供 EXE 交付物。

迁移期间，以现有 dashboard-core.js 测试夹具作为行为基准，把映射规则移植为 Python；同一夹具同时验证看板 JS 与制作器 Python 结果。MVP 后两套入口继续存在，并通过兼容契约和黄金夹具防止行为漂移；是否进一步共享服务不属于 MVP 决策。

### 14.2 性能

- 扫描、哈希和缩略图生成不得运行在 GUI 主线程。
- 图片任务有界并发，优先处理当前可见槽位。
- 映射检查使用虚拟化 Model/View，不为全部照片同时创建控件和图像对象。
- 缩略图缓存键包含源相对路径、大小、mtime、目标尺寸和算法版本。
- 原图缓存使用 LRU 和内存上限。

### 14.3 可靠性与安全

- 默认不联网，不收集遥测，不上传 CSV 和照片。
- 输出路径规范化并做项目根目录边界检查。
- 默认不覆盖同名新项目；更新必须先成功加载原项目。
- 写入采用同盘暂存、校验、备份、原子替换。
- 日志不记录完整敏感行数据；路径日志支持脱敏。
- SQLite 索引损坏时可重建，不影响项目事实文件。

### 14.4 兼容性

- Windows 10/11 x64 为 GUI 首发平台。
- Linux x64 为 CLI 首发平台；Linux ARM64 为 P1。
- 中文路径、空格路径、长路径必须纳入测试。
- 项目 JSON 保持当前 version 1 可读格式，除非另立迁移方案。
- 保留 rows、mappingRows、sourceCsv、photoRoot、mappingMode、mappingFields、mappingViews、photoMappingOverrides、protocolTemplate 和 dashboardConfig 的兼容语义。

## 16. 版本与演进

1. 独立制作器先达到本 PRD 定义的 MVP，并确保看板首页全部现有功能不回归。
2. 使用共享黄金夹具验证顺序、文件夹、左右耳、单耳、空耳、重复和人工覆盖。
3. 通过真实 Windows 项目验收后，独立制作器作为额外入口发布；不改变看板默认首页和操作方式。
4. 后续可优化看板与制作器的代码复用，但不得以此为由取消看板的 CSV/照片/映射/变量分类能力。
5. 上一版 Node/Web Builder 停止作为正式架构演进，只保留 CLI 参数和审计格式参考。

## 19. 用户洞察与问题验证

- 用户明确指出，文本异常计数不足以判断映射正确性；必须看到实际照片及槽位上下文。
- 核心目标是拆分“项目生产”和“看板分析”，不是增加另一个简化入口。
- 用户要求独立入口与看板入口长期并存，尤其必须保留看板内的变量类别更换与照片映射调整。
- 用户在 Windows 上人工测试，同时希望未来在 Linux 上自动运行，因此 GUI 与自动化必须同核。
- 浏览器照片链路已经需要多来源 URL、后端缩略图和缓存等多层优化；独立工具应以文件索引和原生缩略图模型解决，而不是复制同一套 HTML 加载问题。
